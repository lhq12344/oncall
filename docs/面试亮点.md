# OnCall 多 Agent 运维系统 - 面试亮点

> 当前实现一致版。详细口径以 [PROJECT_STRUCTURE.md](/home/lihaoqian/project/oncall/docs/PROJECT_STRUCTURE.md) 为准。

## 亮点一：可中断恢复的 Human-in-the-Loop 工作流

**核心点：高风险动作不是“让模型直接执行”，而是可暂停、可审批、可恢复。**

- 工作流基于 Eino ADK 的 `ResumableAgent` 和 Redis CheckPointStore。
- 变更类命令在 `execute_step` 中会调用 `tool.Interrupt(...)` 主动挂起，等待用户审批。
- 对话链里的 `bash_execute_with_approval`、`request_detail_selection` 也走同样的中断模型。
- 恢复时由控制器调用 `runner.ResumeWithParams(...)`，工具内部通过 `tool.GetResumeContext(...)` 取回 `approved / resolved / comment`。
- Checkpoint 落在 Redis，Key 形如 `oncall:checkpoint:<checkpoint_id>`，默认 TTL 为 24 小时。

**面试可讲价值**

- 把“AI 建议执行”改造成“AI 先停下来，等人确认再执行”。
- 支持断点恢复，不需要整条故障处理链重跑。

## 亮点二：双轨架构 + 分阶段 Multi-Agent 编排

**核心点：系统不是单个大 Agent，而是“对话轨 + 故障处置轨”两条链路。**

### 1. 对话轨

- `chat_stream` 走 `dialogue_agent`
- 负责意图理解、知识检索、K8s/指标查询、受控 Bash 调用

### 2. 故障处置轨

当前工作流真实结构是：

```text
Sequential(
  Loop(
    incident_analysis,
    diagnosis_gate,
    plan,
    plan_gate,
    plan_approval,
    execute_plan,
    verify_plan,
    replan_decider
  ),
  final_report
)
```

- `incident_analysis`：统一完成观测、RCA 和修复意图分析
- `diagnosis_gate`：校验证据、根因和 fallback 是否足以进入计划
- `plan`：生成 canonical ExecutionPlan
- `plan_gate`：校验计划完整性、风险、回滚与成功标准
- `plan_approval`：把用户审批绑定到整份计划快照
- `execute_plan`：只执行已批准的 canonical plan
- `verify_plan`：按 success criteria 验证全计划执行结果
- `replan_decider`：决定完成、重新观测、转人工或终止
- `final_report`：生成最终技术报告并落盘

Loop 最大轮次默认是 `3`，不是无上限自动重试。

**面试可讲价值**

- 把“诊断、计划、审批、执行、验证、重规划”拆开，职责边界清晰。
- 用 `plan_gate`、`verify_plan` 和 `replan_decider` 控制自动化边界，避免模型反复试错。

## 亮点三：三层状态管理，既控 Token，又能恢复长流程

**核心点：会话记忆、执行检查点、工作流状态不是一套东西，而是分层设计。**

### 1. Session Memory

- `internal/context/session_memory.go` + `utility/mem/mem.go`
- 存在 Redis 中，负责普通对话记忆和 token 预算控制
- 超过阈值后会压缩历史：
  - 触发阈值：大于 40 轮
  - 每次压缩：最旧 20 轮
  - 摘要生成：规则拼接 `用户/助手` 历史，不是 LLM 总结
- `KeepReasoningInContext=false`，避免 reasoning/thinking 内容进入持久上下文

### 2. Checkpoint Store

- Redis bytes 存储 ADK checkpoint
- 负责中断恢复，不负责用户对话摘要

### 3. Graph State

- 类型是 `IncidentState`
- 负责在故障工作流里沉淀 observation / RCA / proposal / execution / final report
- 配合 `incidentHistoryRewriter`，后续 Agent 输入只保留“最新用户输入 + 结构化状态”，避免完整 transcript 反复回灌

**补充点**

- `dialogue_agent` 还挂了 Eino 的 summarization middleware，但故障工作流主链的上下文控制核心是 `Graph State + History Rewriter`。

**面试可讲价值**

- 这套拆分既解决上下文成本问题，也解决长流程恢复问题。

## 亮点四：执行安全不是一句“有审批”，而是多层防护

**核心点：系统对执行风险做了静态、运行时、流程级三层控制。**

### 1. 静态风险校验

`validate_plan` 会把命令分成三类：

- 绝对禁止：`rm -rf /`、`mkfs`、`dd if=`、`shutdown/reboot`、fork bomb
- 高风险变更：如 `kubectl delete/scale/patch`、`docker stop/rm`、`systemctl restart`
- 只读操作：如 `kubectl get/describe/logs/top`、`cat/ls/ps/df`

### 2. 运行时审批与执行保护

- `execute_step` 只允许白名单命令
- 变更类步骤执行前必须中断审批
- 命令执行带 timeout
- 输出会裁剪，避免大段日志直接回灌模型

### 3. 流程级收敛控制

- `replan_decider` 负责判断“完成 / 重新观测 / 人工介入 / 终止”
- 同类问题重复失败达到阈值后会停止自动重试
- 当前默认阈值是 `3`

### 4. 最终收口

- `final_reporter` 会生成最终技术报告
- 报告会写入 `logs/ops_reports`
- 成功经验还会归档到 ops 案例库，形成可复用知识

**面试可讲价值**

- 不是“模型想执行就执行”，而是把 AI 约束进一个可审计、可恢复、可中断的工程系统里。

## 30 秒总结话术

这个项目最值得讲的不是“我接了几个 AI 工具”，而是我把故障处理工程化了。系统分成对话轨和运维工作流轨，核心工作流是 `Observation -> RCA -> Ops -> Execution -> Gate -> Strategy -> FinalReport`。高风险步骤会中断等人审批，审批后靠 Redis checkpoint 从断点恢复。状态上把 Session Memory、Checkpoint、Graph State 拆开，既控制 token，又能保证长流程可恢复。执行层再叠加静态风险校验、白名单、逐步审批和重复失败熔断，安全边界比较完整。
