## 一、执行安全链路

### Q1: validate_plan 的静态风险筛查具体怎么实现？风险等级怎么定义？

### 推荐短答

validate_plan 靠正则和规则引擎做静态分析，分三级：Safe / Warning / High / Critical。绝对危险命令直接 blocked，高风险变更进入执行层后还要逐级审批。

### 展开回答

```go
// 典型的风险筛查分层设计
type RiskLevel int
const (
    RiskLevelSafe RiskLevel = iota
    RiskLevelWarning    // 警告类，如配置变更
    RiskLevelHigh        // 高风险，如数据删除、权限变更
    RiskLevelCritical    // 绝对拦截，如 rm -rf /、drop table without where
)

// 筛查维度：
// 1. 命令类型黑名单：rm -rf, drop table, truncate, kill -9
// 2. 参数模式匹配：* --force, * | bash, sensitive data in args
// 3. 业务规则：生产环境禁止 ddl、未审批的脚本执行
// 4. 上下文关联：当前状态+目标命令的组合风险（如磁盘已满时还执行大表扫描）
```

**追问1: 如何避免黑名单被绕过？**

不能只做简单字符串匹配。需要做 tokenize 后做语义分析。比如 `rm -rf /tmp/*` vs `rm -rf /*` 要能区分。要用 AST 解析命令，提取真实执行的路径和参数。

**追问2: 高风险变更触发人工审批的阈值是什么？**

风险等级 `>= High` 时触发 interrupt。审批通过后需携带 approval_token，execute_step 验证 token 有效性才执行。

### 代码落点

- `internal/agent/execution/tools/validate_plan.go`

### Q2: execute_step 的白名单校验是怎么做的？参数校验有哪些手段？

### 推荐短答

白名单按命令+子命令+参数层层约束。参数校验覆盖类型、范围、枚举、正则、依赖五个维度，任何一步没过就不执行。

### 展开回答

```go
// 白名单设计示例
type WhitelistEntry struct {
    CmdPattern string      // 如 "^kubectl$", "^docker$"
    AllowedSubCmds []string // 如 ["get", "describe", "logs"]
    AllowedFlags map[string]bool
    ParamSchemas map[string]ParamSchema // 参数类型约束
}

// 参数校验：
// 1. 类型校验：number/string/bool/array
// 2. 范围校验：port in [1-65535], replicas >= 0
// 3. 枚举校验：env in [prod, staging, dev]
// 4. 正则校验：image tag must match semver
// 5. 依赖校验：if subcmd==scale then --replicas required
```

**追问: 如果参数是动态生成的（如从上一 step 结果获取）怎么处理？**

两层校验。Plan 生成时会做占位符替换，此时做 schema 校验。Execute 时若发现实际值与 schema 偏差（如类型变了），立即 abort 并上报异常。

### 代码落点

- `internal/agent/execution/tools/execute_step.go`

### Q3: validate_result 的语义启发式判断具体指什么？如何区分"真的失败"vs"现场已恢复"？

### 推荐短答

不是简单字符串匹配，而是结合退出码、stderr 语义、现场状态采样、历史模式综合判断。核心是区分"命令执行失败"和"现场状态已变导致计划失配"。

### 展开回答

```go
// 失败类型判断
type ResultType int
const (
    ResultTypeSuccess ResultType = iota
    ResultTypeRealFailure   // 真的失败了，需要 rollback 或转人工
    ResultTypePlanMismatch  // 现场状态已变，计划失配，需要重新 plan
    ResultTypeFalsePositive // 误报，命令本身没问题
)

// 启发式判断依据：
// 1. 退出码 + stderr 语义：exit 1 但 stderr 包含 "Connection refused" -> 可能是临时网络问题
// 2. 幂等性检测：重新执行相同命令是否能成功
// 3. 现场状态采样：执行前查询 target 状态 vs 执行后状态变化是否符合预期
// 4. 历史模式：类似场景过去 100 次的 success rate
// 5. 错误消息分类：可重试错误（timeout、connection refused）vs 不可重试错误（permission denied）
```

**追问: 如果启发式判断错了怎么办？**

设置兜底机制。连续 2 次判断为 `PlanMismatch` 后，强制转人工。另外任何 `PlanMismatch` 都记录，供离线评估启发式准确率。

### 代码落点

- `internal/agent/execution/tools/validate_result.go`

### Q4: rollback 的实现有什么讲究？为什么不能简单执行逆命令？

### 推荐短答

逆命令不总是存在、不一定幂等、可能部分失败。正确做法是快照回滚而非逆命令执行。

### 展开回答

- **逆命令不存在**：`kubectl delete` 的逆命令是什么？重新 `apply`？那要保存原始 manifest
- **幂等性问题**：rollback 本身可能失败，要支持重入
- **状态快照**：建议在 execute_step 前做 checkpoint，rollback 到快照而非执行逆命令
- **部分回滚**：如果有 5 步，第 3 步失败，回滚 1-2 步还是 3-5 全部回滚？需要业务语义决定
- **超时控制**：rollback 也可能卡住，要有独立的 timeout

### 代码落点

- `internal/agent/execution/tools/rollback.go`

## 二、状态管理与可恢复性

### Q5: 三层状态（Session Memory / Graph State / Redis Checkpoint）的职责边界是什么？为什么需要三层？

### 推荐短答

Session Memory 管 token 预算和对话历史，Graph State 管结构化流程状态，Redis Checkpoint 管断点持久化。分层是因为访问频率和数据生命周期不同。

### 展开回答

```
Session Memory（内存）:
- 用途：单次请求的生命周期内，存 token 计数、模型 context window 位置
- 生命周期：请求结束即销毁
- 数据量：小（几十 KB）
- 例子：当前 loop 第几轮、已消耗的 token 数

Graph State（内存/Redis）:
- 用途：结构化流程状态，如当前在哪个 Node、哪些 Edge 已执行、局部变量
- 生命周期：整个 session 存活期间
- 数据量：中等（几百 KB）
- 例子：RCA 分析结果、生成的候选 Plan 列表

Redis Checkpoint（持久化）:
- 用途：高风险步骤中断后的断点恢复
- 生命周期：跨 session 存在，可主动删除
- 数据量：大（MB 级别，存完整上下文和中间结果）
- 触发条件：interrupt 发生时自动落盘
```

**追问: 为什么 Graph State 不能统一放 Redis？**

性能。Graph State 访问频率极高（每个 step 都要读写），Redis 往返延迟在 ms 级别，内存访问是 ns 级别。分离后，热点数据走内存，冷数据走 Redis。

### 代码落点

- `internal/context/session_memory.go`
- `internal/agent/ops/state_bridge.go`
- `internal/context/checkpoint_store.go`

### Q6: interrupt / resume 的具体流程是什么？checkpoint_id 和 interrupt_id 的关系是什么？

### 推荐短答

中断时保存 checkpoint + interrupt 记录，恢复时验证 approval_token 后从 checkpoint 恢复。checkpoint_id 是状态快照，interrupt_id 是中断事件，两者一一对应。

### 展开回答

```
Interrupt 触发流程：
1. execute_step 检测到高风险操作
2. 写入 interrupt record: {interrupt_id, checkpoint_id, interrupt_reason, pending_approvals}
3. 暂停 Graph State 执行，返回 interrupt 事件到前端
4. 前端展示审批 UI，等待人工

Resume 流程：
1. 人工审批通过，携带 approval_token 调用 resume 接口
2. Backend 验证 token -> 加载 checkpoint_id 对应的 CheckpointStore
3. 恢复 Graph State 到中断点
4. 继续执行后续步骤
```

```
checkpoint_id: 唯一标识一个可恢复状态快照（包含完整的 Graph State + 中间结果）
interrupt_id: 唯一标识一次中断事件（包含中断原因、审批状态、checkpoint 引用）

关系：1 interrupt_id -> 1 checkpoint_id（中断时保存）
     1 checkpoint_id -> N interrupt_id（同一个断点可能被多次中断？）
     实际上：1 checkpoint 只能对应 1 个 active interrupt
```

**追问: 如果审批拒绝怎么办？**

中断记录标记为 rejected，不执行后续步骤，session 进入最终态。所有中间状态保留供审计。

### 代码落点

- `internal/controller/chat/chat_v1.go`
- `internal/agent/execution/tools/execute_step.go`

### Q7: Redis Checkpoint 的存储结构是什么？如何保证一致性？

### 推荐短答

key 设计用命名空间分隔，一致性靠 Redis Transaction + WAL 保证，恢复时校验版本匹配。

### 展开回答

```
Key 设计：
checkpoint:{session_id}:{checkpoint_id}  -> JSON(GraphState + Variables + Metadata)
interrupt:{interrupt_id}                 -> JSON(InterruptRecord)
session:meta:{session_id}                 -> Hash(CurrentNode, LoopCount, etc.)

一致性保证：
1. 写入 Checkpoint 前先写 Redo Log（WAL）
2. Interrupt 原子写入：checkpoint + interrupt record 用 Redis Transaction (MULTI/EXEC)
3. 恢复时校验 checkpoint_version 与 interrupt_version 匹配
4. 定期清理：已完成的 session 最多保留 7 天
```

### 代码落点

- `internal/context/checkpoint_store.go`

## 三、SSE 实时交互与协议

### Q8: SSE 事件语义（content/step/interrupt/error/done）的使用场景是什么？为什么需要 JSON 和文本双模式？

### 推荐短答

JSON 模式用于结构化渲染，文本模式用于降级和简单客户端可读。网络抖动时文本回退保证基本感知。

### 展开回答

```
content: 增量内容输出，如模型推理的中间结果、流式日志
step:    流程节点切换，如 "进入 RCA 分析" -> "进入 Plan 生成"
interrupt: 人工审批触发，前端需渲染审批卡片
error:   不可恢复错误，流程终止
done:    正常结束

JSON 模式：结构化数据，前端好解析，适合精确渲染
文本模式："[DONE]" / "[ERROR] reason" / "[INTERRUPT]"
         - 用于网络不稳定时的降级
         - 用于简单客户端（如 curl）可读
         - 用于日志记录时直接打印
```

**追问: 网络抖动时如何保证中断不丢失？**

Client 重连时携带 last_event_id，Server 从该 ID 之后的 checkpoint 恢复并补发丢失的 events。Server 端 buffer 最近 100 条 events（TTL 5 分钟）。

### 代码落点

- `internal/controller/chat/chat_v1.go`
- `Front_page/src/services/api.ts`

### Q9: 前端断线重连后，后端如何判断从哪个 checkpoint 恢复？

### 推荐短答

Client 携带 Last-Event-ID header，后端查找对应 checkpoint，存在则 replay 丢失事件并继续，不存在则返回 410 Gone。

### 展开回答

```
Client 重连时：
1. 携带 header "Last-Event-ID: {checkpoint_id}"
2. 后端查找该 ID 对应的 checkpoint
3. 若存在：replay 丢失的 events -> 恢复 Graph State -> 继续 SSE
4. 若不存在：返回 410 Gone，前端需重新开始

Server 端处理：
- 每个 SSE event 都有递增的 event_id（等于 checkpoint_id）
- Server buffer 维护 event_id -> content 映射
- 重连后先发 "recovery: {from_id}" 事件告知前端进入恢复模式
```

### 代码落点

- `internal/controller/chat/chat_v1.go`

## 四、全链路架构设计

### Q10: Loop（Ops + Execution 迭代）的终止条件是什么？为什么上限是 3 轮？

### 推荐短答

3 轮以内未能解决的案子，80% 是需要人工判断的复杂场景。超过 3 轮强制转人工，防止无限重试。

### 展开回答

```
Loop 迭代逻辑：
while (current_phase in [Ops, Execution]) and (loop_count < MAX_LOOPS):
    1. Ops: 观测数据 -> 生成/更新 Plan
    2. Execution: 执行 Plan -> validate_result
    3. 根据结果决定：继续 loop / 退出到人工 / 流程结束

终止条件（满足任一即终止）：
1. loop_count >= 3
2. validate_result 返回 Success
3. validate_result 返回 RealFailure（无可行替代方案）
4. 人工介入（审批拒绝 / 主动打断）

上限 3 轮的理由：
- 经验值：生产故障处置中，3 轮以内以内未能解决的案子，80% 是需要人工判断的复杂场景
- 防止：AI 在复杂场景下无限循环重试，延误处置时机
- 成本：每轮 loop 都有 token 消耗和执行成本
```

- `internal/agent/ops/incident_nodes.go`

### Q11: 如何定义"AI 自动化边界"？哪些步骤必须人工确认？

### 推荐短答

写操作、权限变更、生产配置、外部依赖调用、脚本执行必须人工。只读操作、预审批操作、可回滚写可以自动。

### 展开回答

```
强制人工边界（interrupt）：
1. 数据写操作：DELETE、DROP、TRUNCATE、UPDATE affecting > 100 rows
2. 权限变更：grant/revoke、role change、credential rotation
3. 生产环境配置：非 /tmp 路径下的配置修改
4. 外部依赖：调用第三方 API（费用/副作用不可控）
5. 脚本执行：下载并执行外部脚本

可以自动化的边界：
1. 只读操作：SELECT、GET、DESCRIBE、logs
2. 可回滚的写：CREATE（可 drop）、ALTER（可 alter back）
3. 预审批过的操作：白名单内的 kubectl 命令、已审批的 runbook
4. 观测动作：metrics 采集、trace 收集、log 分析

边界动态调整：
- 随团队成熟度调整：初期人工边界宽，后期可收紧
- 随环境调整：dev 环境可自动化，prod 必须人工
```

### Q12: 从 Observation 到 Strategy 的完整流程中，各阶段的数据流转是什么？

### 推荐短答

Observation 采集事件，RCA 分析根因，Ops 生成计划，Execution 执行验证，Strategy 复盘沉淀。

### 展开回答

```
Observation:
  输入：告警原始数据（metrics/logs/traces）
  输出：结构化事件 {event_type, severity, involved_entities}
  关键技术：数据清洗、事件关联、时序分析

RCA (Root Cause Analysis):
  输入：Observation 结果 + 历史知识库
  输出：根因报告 {cause_node, confidence, evidence, related_events}
  关键技术：因果图构建、异常点定位、知识检索

Ops (Operations Planning):
  输入：RCA 结果 + 可用工具清单 + 环境上下文
  输出：候选 Plan A/B/C（含风险评估和执行步骤）
  关键技术：多目标优化、风险评估

Execution:
  输入：选中的 Plan
  输出：执行结果 {step_results, validation_results}
  关键技术：白名单校验、增量执行、rollback

Strategy (复盘与知识沉淀):
  输入：完整执行记录 + 执行结果
  输出：复盘报告 + 知识条目（更新知识库）
  关键技术：模式识别、教训提取、best practice 归纳
```

### 代码落点

- `internal/agent/ops/incident_nodes.go`
- `internal/agent/execution/agent.go`
- `internal/agent/rca/agent.go`
- `internal/agent/strategy/agent.go`

## 五、工程细节追问

### Q13: GoFrame + Eino ADK 的角色分工是什么？为什么选这个组合？

### 推荐短答

GoFrame 做 Web 框架层（HTTP/SSE/路由/ORM），Eino ADK 做 Agent 框架层（LLM 调用/Tool 编排/状态管理）。选型理由是 Go 生态成熟、两框架轻量可定制。

### 展开回答

```
GoFrame:
- 定位：Web 框架（HTTP/SSE/路由/中间件/ORM）
- 负责：API 入口、请求分发、配置管理、日志

Eino ADK:
- 定位：Agent 开发框架（LLM 调用、Tool 调用、Chain 编排）
- 负责：模型推理调用、Tool 注册、状态管理、Loop 控制

选型理由：
1. GoFrame 成熟稳定，生态完整，适合工程化生产项目
2. Eino ADK 提供 Agent 需要的 callback 机制、stream 支持
3. 两者都是 Go 生态，减少多语言栈复杂度
4. 对比 LangChain Go：Eino 更轻量，定制性更强
```

### Q14: 如果让你优化 OnCall 的 token 消耗，你会在哪里下手？

### 推荐短答

Session Memory 层做动态压缩，Graph State 层做增量传递，Checkpoint 层做懒加载和分片，Loop 层做早期退出。

### 展开回答

```
优化方向：
1. Session Memory 层：
   - 动态 context 压缩：只保留关键的历史步骤摘要
   - RAPTOR-like 层次索引：按相关性召回，而非全量输入

2. Graph State 层：
   - 增量 vs 全量：只传递 delta，而非每次都传完整 state
   - 中间结果压缩：embed 并存储，而非原文

3. Checkpoint 层：
   - 懒加载：只加载本次 resume 需要的部分 checkpoint
   - 分片存储：大 checkpoint 拆分，过期部分不加载

4. Loop 层面：
   - 早期退出：Plan 生成后若置信度 > 0.95，跳过备选方案
   - 缓存复用：相同场景的 Plan 模板缓存
```

## 面试总结话术

这个项目最值得讲的，不是"接了多少 AI 工具"，而是我把故障处理流程做成了一套真正可运行的工程系统。

它有双轨架构（对话轨 + 运维轨），有可恢复的中断审批（interrupt/resume + checkpoint），有分层状态管理（三层状态各司其职），也有计划级安全控制（plan_gate + plan_approval + execute_step + verify_plan + replan_decider）。

**如果用一句话总结**，我做的不是"会回答运维问题的聊天机器人"，而是**一套能在真实故障场景里诊断、计划、审批、执行、验证、恢复和沉淀经验的多 Agent 运维工作流**。

**最核心的价值**是把 AI 自动化边界做清楚了：该自动化的步骤能自动推进，该人工确认的步骤必须中断审批，而且全流程可追踪、可恢复、可复盘。
