# OnCall 项目介绍

> 当前实现一致版。主文档见 [PROJECT_STRUCTURE.md](/home/lihaoqian/project/oncall/docs/PROJECT_STRUCTURE.md)。

## 1. 项目定位

`OnCall` 是一个面向 Kubernetes / SRE / 值班运维场景的多 Agent 智能运维系统，不是普通聊天机器人。

它要解决的是一个典型运维问题：故障处理通常要在 `kubectl`、Prometheus、Elasticsearch、历史案例、知识库、命令行之间来回切换，定位慢、执行风险高、知识难沉淀。
这个项目把这条链路工程化成了一个完整闭环：

```text
自然语言入口
  -> 观测采集
  -> 根因分析
  -> 修复提案
  -> 命令执行与审批
  -> 最终技术报告
  -> 知识沉淀
```

一句话介绍：

> OnCall 是一个基于 GoFrame + Eino ADK 构建的多 Agent 运维系统，能够围绕 Kubernetes 故障场景完成观测、RCA、执行审批、报告生成和知识沉淀的闭环。

## 2. 设计目标

### 2.1 要解决的实际问题

- 故障信息分散在多数据源里，人工切换成本高
- 大模型容易“会说不会做”，缺少受控执行能力
- 高风险命令不能直接交给模型执行，必须有人确认
- 故障处理是长流程，执行过程中可能中断、审批、断线、恢复
- 一次处理经验如果不沉淀，下次还会重复从头分析

### 2.2 系统目标

- 用自然语言统一运维入口
- 用多 Agent 分层降低复杂任务耦合
- 用工具获取事实，而不是让模型猜
- 用审批、校验、白名单、熔断保证执行安全
- 用报告和知识库把一次排障变成长期资产

## 3. 技术栈

| 层次 | 技术 |

| Web 层 | GoFrame v2 |

## 4. 系统架构

### 4.1 双轨架构

系统当前不是单一 Agent，而是两条主链路并存：

```text
Frontend
  -> Controller + ADK Runner
     ├─ 对话轨：dialogue_agent
     └─ 运维轨：incident_workflow_agent
```

### 4.2 对话轨

- 接口：`POST /api/v1/chat_stream`
- 恢复：`POST /api/v1/chat_resume_stream`
- 目标：处理普通对话、轻量运维查询、知识检索、受控命令执行

对话轨主要能力：

- 意图识别
- 缺失上下文补充
- K8s / Prometheus 查询
- 知识检索和案例检索
- Web 搜索
- Bash 审批执行

### 4.3 运维轨

- 接口：`POST /api/v1/ai_ops_stream`
- 恢复：`POST /api/v1/ai_ops_resume_stream`
- 目标：跑完整故障处置闭环

真实工作流是：

```text
Sequential(
  observation_collector,
  rca_agent,
  Loop(
    ops_agent,
    execution_agent,
    execution_gate
  ),
  strategy_agent,
  final_reporter
)
```

Loop 的最大迭代次数默认是 `3`。

## 5. 多 Agent 分工

### 5.1 Dialogue Agent

文件：`internal/agent/dialogue/agent.go`

职责：

- 理解用户意图
- 选择合适工具
- 输出终端式、面向用户的回答

工具集包括：

- `intent_analysis`
- `request_detail_selection`
- `knowledge_retrieve`
- `ops_case_retrieve`
- `bash_execute_with_approval`
- `web_search`
- `k8s_monitor`
- `metrics_collector`

### 5.2 Knowledge Agent

文件：`internal/agent/knowledge/agent.go`

职责：

- 处理 `/api/v1/upload`
- 对上传文本做分片与索引
- 写入知识库 / 向量库

它不是对象存储文件服务，而是知识上传链路。

### 5.3 Observation Collector

文件：`internal/agent/ops/incident_observer.go`

职责：

- 在 RCA 前先采集基础观测快照
- 聚合 K8s / Prometheus / Elasticsearch 的当前状态
- 把结果写入 `IncidentState`

### 5.4 RCA Agent

文件：`internal/agent/rca/agent.go`

职责：

- 基于当前观测快照做根因分析
- 输出结构化 RCA 结果，而不是自由文本猜测

主要输出：

- `root_cause`
- `target_node`
- `path`
- `impact`
- `confidence`
- `evidence`

### 5.5 Ops Agent

文件：`internal/agent/ops/agent.go`

职责：

- 根据 RCA 和执行反馈生成 `RemediationProposal`
- 负责“修复策略提案”，不负责真正执行

重点：

- 输出的是修复策略，不是最终命令级执行计划
- 如果运行时现场和旧假设不一致，会调整策略

### 5.6 Execution Agent

文件：`internal/agent/execution/agent.go`

职责：

- 把修复提案转成命令级计划
- 做风险校验、执行、结果验证、必要时回滚

工具链是：

```text
normalize_plan
  -> generate_plan
  -> validate_plan
  -> execute_step
  -> validate_result
  -> rollback
```

### 5.7 Execution Gate

文件：`internal/agent/ops/incident_nodes.go`

职责：

- 判断当前执行结果是否要结束循环
- 是否需要重新规划
- 是否需要人工介入
- 是否触发重复失败熔断

### 5.8 Strategy Agent + Final Reporter

- `strategy_agent`：负责复盘、评估和知识更新
- `final_reporter`：负责生成最终技术报告，并把报告写入 `logs/ops_reports`

## 6. 流式通信与中断恢复

### 6.1 为什么用 SSE

因为这个项目的核心交互是“后端持续往前端推过程状态”，包括：

- 内容 chunk
- 步骤进度
- 中断审批
- 完成信号

SSE 相比 WebSocket 更简单，HTTP 兼容性更好，也更适合当前单向推流场景。

### 6.2 SSE 事件模型

对话链主要输出：

- 普通文本 chunk
- `interrupt`
- `[DONE]`
- `[ERROR]`

运维链主要输出：

- `step`
- `content`
- `interrupt`
- `done`
- `error`

### 6.3 中断恢复机制

高风险步骤不会直接执行，而是走“中断 -> 审批 -> 恢复”模型：

1. 工具层检测到需要审批
2. `tool.Interrupt(...)` 挂起工作流
3. 前端收到 `interrupt` 事件并渲染卡片
4. 用户提交 `approved / resolved / comment`
5. 控制器调用 `runner.ResumeWithParams(...)`
6. 工具通过 `tool.GetResumeContext(...)` 获取用户决策
7. 从原断点继续执行

## 7. 状态管理设计

### 7.1 Session Memory

文件：

- `internal/context/session_memory.go`
- `utility/mem/mem.go`

作用：

- 保存普通对话历史
- 控制 token 预算
- 压缩旧历史，避免上下文无限增长

当前实现要点：

- Redis 存储
- 历史轮次超过 40 轮时开始压缩
- 每次压缩最旧 20 轮
- 摘要是规则拼接，不是 LLM 总结
- `KeepReasoningInContext=false`

### 7.2 Checkpoint Store

文件：`internal/context/checkpoint_store.go`

作用：

- 保存 ADK Runner checkpoint
- 支持中断后恢复执行

当前实现：

- Redis key：`oncall:checkpoint:<checkpoint_id>`
- 默认 TTL：24 小时

### 7.3 Graph State

文件：`internal/agent/ops/state_bridge.go`

作用：

- 在故障工作流里沉淀结构化状态
- 让下游 Agent 读状态，而不是反复读完整 transcript

核心字段包括：

- observation 快照
- RCA 结果
- proposal 信息
- execution 状态与原因
- final status / final report

## 8. 执行安全设计

### 8.1 静态风险校验

`validate_plan` 负责命令级计划风险判断：

- 禁止 destructive 命令
- 标记高风险变更命令
- 放行只读命令

### 8.2 运行时保护

`execute_step` 负责：

- 白名单命令校验
- 超时控制
- 输出裁剪
- 变更类命令审批

### 8.3 流程级收敛

`execution_gate` 负责：

- 成功则结束循环
- 失败则重规划
- 重复问题达到阈值则转人工

当前默认重复失败上限是 `3`。

## 9. 可观测性与事实驱动

这个项目强调“先看事实，再下结论”。

主要事实来源：

- Kubernetes 资源状态
- Prometheus 指标
- Elasticsearch 日志
- 历史案例库
- 知识库
- 必要时外部 Web 搜索

系统设计原则是：

- 优先工具观测
- 证据优先于猜测
- 最新现场优先于旧推断

## 10. 最值得讲的工程点

### 10.1 不是“一个大模型”，而是双轨多 Agent 系统

- 职责拆分清晰
- 流程边界清楚
- 更容易控风险

### 10.2 中断恢复做成了真实工程能力

- 可暂停
- 可审批
- 可恢复
- 可断点继续

### 10.3 状态分层设计比较完整

- Session Memory 管对话记忆
- Checkpoint 管执行恢复
- Graph State 管结构化工作流状态

### 10.4 执行安全边界不是口头承诺

- 静态风险校验
- 运行时审批
- 重复失败熔断
- 最终人工兜底

## 11. 面试时的标准介绍版本

可以这样介绍：

> OnCall 是一个面向 Kubernetes 值班运维的多 Agent 系统。它不是单纯问答，而是把故障处理拆成了两条链路：一条是 `dialogue_agent` 对话链，负责意图识别、检索和轻量工具调用；另一条是 `incident_workflow_agent`，按 `Observation -> RCA -> Ops -> Execution -> Gate -> Strategy -> FinalReport` 跑完整处置闭环。
> 在工程上我重点做了三件事：第一，用 Redis Checkpoint + ADK Resume 实现高风险步骤中断审批和断点恢复；第二，用 Session Memory、Graph State、Execution Tool State 分层管理状态，既控制 token，又支持长流程恢复；第三，用 `validate_plan + execute_step + execution_gate` 把执行安全做成可校验、可中断、可熔断的机制。

## 13. 总结

这个项目最像后端工程而不是“Prompt Demo”的地方，在于它把故障处理过程真正做成了一个受控系统：有分层、有状态、有恢复、有审批、有熔断，也有最终的知识沉淀。对外看是 AI 运维，对内本质上是一套可执行、可审计、可恢复的工程化工作流。
