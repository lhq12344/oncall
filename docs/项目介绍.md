# OnCall 项目介绍

## 1. 项目定位

`OnCall` 是一个面向 Kubernetes / SRE / 值班运维场景的多 Agent 智能运维系统，不是普通聊天机器人。

它要解决的是一个典型运维问题：故障处理通常要在 `kubectl`、Prometheus、Elasticsearch、历史案例、知识库、命令行之间来回切换，定位慢、执行风险高、知识难沉淀。
这个项目把这条链路工程化成了一个完整闭环：

```text
自然语言入口
  -> 诊断与证据采集
  -> canonical 计划生成
  -> 计划校验与整体审批
  -> 受控执行
  -> 全计划验证与必要重规划
  -> 最终报告与知识沉淀
```

一句话介绍：

> OnCall 是一个基于 GoFrame + Eino ADK 构建的多 Agent 运维系统，能够围绕 Kubernetes 故障场景完成诊断、计划、审批、执行、验证、重规划、报告生成和知识沉淀的闭环。

## 2. 设计目标

### 2.1 要解决的实际问题

- 故障信息分散在多数据源里，人工切换成本高
- 大模型容易“会说不会做”，缺少受控执行能力
- 高风险命令不能直接交给模型执行，必须有人确认
- 故障处理是长流程，执行过程中可能中断、审批、断线、恢复
- 一次处理经验如果不沉淀，下次还会重复从头分析

### 2.2 系统目标

- 用自然语言统一运维入口
- 用多 Agent 分层降低复杂任务耦合
- 用工具获取事实，而不是让模型猜
- 用审批、校验、白名单、熔断保证执行安全
- 用报告和知识库把一次排障变成长期资产

## 4. 系统架构

### 4.1 双轨架构

系统当前不是单一 Agent，而是两条主链路并存：

```text
Frontend
  -> Controller + ADK Runner
     ├─ 对话轨：dialogue_agent
     └─ 运维轨：incident_workflow_agent
```

### 4.2 对话轨

- 接口：`POST /api/v1/chat_stream`
- 恢复：`POST /api/v1/chat_resume_stream`
- 目标：处理普通对话、轻量运维查询、知识检索、受控命令执行

对话轨主要能力：

- 意图识别
- 缺失上下文补充
- K8s / Prometheus 查询
- 知识检索和案例检索
- Web 搜索
- Bash 审批执行
- Slash 命令（`/help`、`/k8s`、`/diagnose`、`/ops` 等）

### 4.3 运维轨

- 接口：`POST /api/v1/ai_ops_stream`
- 恢复：`POST /api/v1/ai_ops_resume_stream`
- 目标：跑完整故障处置闭环

真实工作流（基于 `agentteams` 编排）：

```text
Loop(
  incident_analysis,     // 观测 + RCA + 修复意图（按需选择诊断工具）
  diagnosis_gate,        // 校验证据、根因、影响面与 fallback
  plan,                  // 生成 canonical ExecutionPlan
  plan_gate,             // 校验计划风险、回滚、成功标准与审批边界
  plan_approval,         // 绑定整份 plan snapshot 的审批
  execute_plan,          // 仅执行已批准的 canonical plan
  verify_plan,           // 验证全计划执行结果
  replan_decider         // 决定完成 / 重新观测 / 转人工 / 终止
),
final_report             // 汇总诊断、计划、执行、验证与重规划过程并归档
```

Loop 的最大迭代次数默认是 `3`（`agentteams.DefaultLoopMaxIterations`）。

## 5. 多 Agent 分工

### 5.1 Dialogue Agent

文件：`internal/agent/dialogue/agent.go`、`internal/agent/dialogue/tools/`

职责：

- 理解用户意图
- 选择合适工具
- 输出终端式、面向用户的回答
- 支持 slash 命令解析与分发

工具集包括：

- `intent_analysis`
- `request_detail_selection`
- `knowledge_retrieve`
- `ops_case_retrieve`
- `bash_execute_with_approval`（接入权限系统）
- `web_search`（serper / searxng）
- `k8s_monitor`
- `metrics_collector`

其中 `k8s_monitor` / `metrics_collector` 是条件注册：K8s 配置或 Prometheus 地址不可用时自动跳过（`agent.go` 中构造失败即降级不注册）。

### 5.2 Knowledge Agent

文件：`internal/agent/knowledge/agent.go`

职责：

- 处理 `/api/v1/upload`
- 对上传文本做分片与索引
- 写入知识库 / 向量库

它不是对象存储文件服务，而是知识上传链路。

上传链路（Eino graph，`internal/agent/knowledge/orchestration.go`）：

```text
file_loader -> markdown_splitter -> milvus_indexer
```

- 分片用 MarkdownSplitter，Embedding 用 Doubao（Ark），写入 Milvus
- 检索侧由 Milvus Retriever + `ranker`（`internal/agent/knowledge/ranker.go`）提供

### 5.3 Incident Agent（运维轨主节点）

文件：`internal/agent/ops/agent.go`

职责：

- 在 RCA 前通过诊断工具采集基础观测事实
- 按需选择诊断工具，完成观测、根因分析、修复提案生成
- 把结果写入 `IncidentState`（Graph State）

诊断工具集（`diagnostic_toolset.go`，deferred 按需加载）：

- `k8s_monitor`
- `metrics_collector`
- `es_log_query`
- `time_query`、`build_dependency_graph`、`correlate_signals`、`infer_root_cause`、`analyze_impact`（来自 `internal/agent/rca/tools/`）

### 5.4 RCA Agent（工具化，不再独立成节点）

文件：`internal/agent/rca/agent.go`、`internal/agent/rca/tools/`

职责：

- 以工具形式提供根因分析能力（`infer_root_cause`、`correlate_signals` 等）
- 输出结构化 RCA 结果，而不是自由文本猜测

注：`internal/agent/rca/agent.go` 中仍保留独立的 `rca_agent` 定义（`NewRCAAgent`，自带 7 个工具），但当前未被装配进运行链路（无调用方）——工作流里的 RCA 能力以工具形式被 incident 节点复用。

主要输出：

- `root_cause`
- `target_node`
- `path`
- `impact`
- `confidence`
- `evidence`

### 5.5 Diagnosis Gate（诊断门）

文件：`internal/agent/ops/diagnosis_gate.go`

职责：

- 在进入计划阶段前校验 incident 证据是否充分、根因是否可信、修复意图是否完整
- 诊断不合法时阻止进入 plan，要求重新观测/诊断

### 5.6 Plan / Plan Gate / Plan Approval

文件：`internal/agent/ops/plan_agent.go`、`internal/agent/ops/plan_gate.go`

职责：

- `plan` 生成 canonical `ExecutionPlan` 并写入 `PlanState`
- `plan_gate` 校验计划完整性、风险、回滚步骤、成功标准和审批边界
- `plan_approval` 把用户审批绑定到 `plan_id + plan_revision + approval_snapshot_hash`

计划阶段工具链是：

```text
normalize_plan
  -> generate_plan
  -> validate_plan
```

### 5.7 Execute Plan / Verify Plan / Replan Decider

文件：`internal/agent/execution/agent.go`、`internal/agent/execution/tools/`、`internal/agent/ops/incident_nodes.go`

职责：

- `execute_plan` 只消费已通过 gate 且已审批的 canonical plan，不再生成计划
- 执行工具只保留 `execute_step -> validate_result -> rollback`
- `verify_plan` 校验 executed_steps 覆盖率与 canonical success criteria
- `replan_decider` 输出 complete / refresh_observation / manual_required / abort
- 重复失败达到默认上限 `3`（`maxRepeatedIssueRetries`）后转人工

### 5.8 Final Report

文件：`internal/agent/ops/incident_nodes.go`（`final_report` 节点）

职责：

- 读取 Graph State 生成最终技术报告
- 把报告写入 `logs/ops_reports`

### 5.9 Strategy Agent（预留，当前未接线）

文件：`internal/agent/strategy/agent.go`、`internal/agent/strategy/tools/`

职责（设计意图）：

- 评估与优化处置策略（`evaluate_strategy`、`optimize_strategy`）
- 把排障经验沉淀进知识库（`update_knowledge`，直接读取 `incident_graph_state`）
- 清理低质量知识（`prune_knowledge`）

当前状态：代码已实现且有测试，但 bootstrap 尚未装配（无调用方）。目前"知识沉淀"闭环实际由 final_report 落盘 `logs/ops_reports` + `ops_case_retrieve` 案例检索承担，Strategy Agent 是后续补全闭环的预留节点。

## 6. 流式通信与中断恢复

### 6.1 为什么用 SSE

因为这个项目的核心交互是“后端持续往前端推过程状态”，包括：

- 内容 chunk
- 步骤进度
- 中断审批
- 完成信号

SSE 相比 WebSocket 更简单，HTTP 兼容性更好，也更适合当前单向推流场景。

### 6.2 SSE 事件模型

对话轨主要输出：

- `content`
- `interrupt`（审批卡片）
- `[ERROR]`
- `[DONE]`

运维轨主要输出：

- `step`
- `content`
- `interrupt`
- `done`
- `error`

### 6.3 中断恢复机制

高风险步骤不会直接执行，而是走“中断 -> 审批 -> 恢复”模型：

1. 工具层检测到需要审批
2. `tool.Interrupt(...)` 挂起工作流
3. 前端收到 `interrupt` 事件并渲染卡片
4. 用户提交 `approved / resolved / comment`
5. 控制器调用 `runner.ResumeWithParams(...)`
6. 工具通过 `tool.GetResumeContext(...)` 获取用户决策
7. 从原断点继续执行

## 7. 状态管理设计

### 7.1 Session Memory

文件：

- `internal/context/session_memory.go`
- `utility/mem/mem.go`

作用：

- 保存普通对话历史
- 控制 token 预算（输入上限 96000 / 输出预留 8192，`mem.Config` 在 main.go 初始化）
- 压缩旧历史，避免上下文无限增长

当前实现要点：

- Redis 存储
- 历史轮次超过 40 轮时开始压缩（`SummarizeAfterTurns: 40`）
- 每次压缩最旧 20 轮（`MaxRecentTurns: 20`）
- 摘要是规则拼接，不是 LLM 总结
- `KeepReasoningInContext=false`

### 7.2 实时上下文压缩（compact 中间件）

文件：`internal/compact/compact.go`、`internal/compact/recovery.go`

作用：

- 对 ADK ChatModelAgent 调用做实时上下文压缩（Mew 风格）
- 用真实 provider usage 与 token 估算混合锚定，避免超出上下文窗口
- 支持软失败降级与恢复（`SoftFailureLimit: 2`）

与 Session Memory 的分工：

- Session Memory 管跨轮对话历史的规则化裁剪
- compact 中间件管单轮 Agent 调用过程中的实时上下文窗口控制

### 7.3 Checkpoint Store

文件：`internal/context/checkpoint_store.go`

作用：

- 保存 ADK Runner checkpoint
- 支持中断后恢复执行

当前实现：

- Redis key：`oncall:checkpoint:<checkpoint_id>`
- 默认 TTL：24 小时

### 7.4 Graph State

文件：`internal/agent/ops/state_bridge.go`

作用：

- 在故障工作流里沉淀结构化状态（session key `incident_graph_state`）
- 让下游 Agent 读状态，而不是反复读完整 transcript

核心字段包括：

- observation 快照（namespace / time range / summary / errors）
- RCA 结果（root cause / target node / path / impact / confidence / evidence）
- Remediation 提案（proposal id / summary / risk / fallback / actions）
- Incident Contract（valid / issues）
- execution 状态（status / success / step count / reason / plan / logs）
- repeated issue 熔断（key / reason / retry count / limit）
- final status / final report

## 8. 执行安全设计

### 8.1 权限系统（permissions）

文件：`internal/permissions/permissions.go`

作用：

- 工具调用前的统一权限决策模型
- 三种决策效果：`allow` / `deny` / `ask`
- 四种权限模式：`default` / `acceptEdits` / `plan` / `bypassPermissions`
- 工具按类别（`read` / `write` / `command`）映射到决策

危险命令模式库（内置正则）：

- 递归强制删除根目录、格式化磁盘、直接写磁盘设备
- 递归 chmod 根目录、fork bomb、管道执行远程脚本
- `git push --force`、`git reset --hard`、`git clean -f` 等
- shutdown / reboot / halt / poweroff 等系统电源操作

除 Bash 审批外，还有三层安全机制：

- 工具级统一网关：`internal/agent/toolkit/` 的 `BuildAlwaysEinoTools` 会把 Agent 的**所有**工具包一层 `DeferredEinoTool` + 权限 Checker，任何工具调用都先过权限决策（allow / deny / ask），deny / ask 在网关层直接拦截或触发 `tool.Interrupt` 审批流——不只 `bash_execute_with_approval` 和 `execute_step`。
- 路径沙箱（`PathSandbox`）：文件写类工具受 `allowedRoots` / `denyWrite` 约束，越界路径直接拒绝。
- 用户级规则文件：`~/.oncall/permissions.yaml` 可追加个性化权限规则。

### 8.2 静态风险校验

`validate_plan` 负责命令级计划风险判断：

- 禁止 destructive 命令
- 标记高风险变更命令
- 放行只读命令

### 8.3 运行时保护

`execute_step` 负责：

- 白名单命令校验
- 超时控制
- 输出裁剪
- 变更类命令审批（接入权限系统）

### 8.4 流程级收敛

`verify_plan` + `replan_decider` 负责：

- 成功则结束循环并进入 final_report
- 执行/验证失败则生成结构化 ReplanDecision
- 需要重规划时回到重新观测，不跳过 diagnosis
- 重复问题达到阈值则转人工

当前默认重复失败上限是 `3`（`maxRepeatedIssueRetries`）。

## 9. 可观测性与事实驱动

这个项目强调“先看事实，再下结论”。

主要事实来源：

- Kubernetes 资源状态
- Prometheus 指标
- Elasticsearch 日志
- 历史案例库
- 知识库
- 必要时外部 Web 搜索

系统设计原则是：

- 优先工具观测
- 证据优先于猜测
- 最新现场优先于旧推断

### 9.1 主动日志采集（PodLogShipper）

文件：`internal/agent/ops/pod_log_shipper.go`

作用：后台周期任务把指定命名空间的 K8s Pod 日志**主动写入 Elasticsearch**，让 `es_log_query` 能查到尚未被外部日志链路采集的现场日志。

- 配置项：`log_sync.enabled / namespaces / interval / tail_lines / index_prefix`（config.yaml）
- 默认：30s 间隔、每 Pod 抓 200 行、命名空间 `infra`、索引前缀 `logs-k8s`
- `log_sync.enabled=false` 时不启动（bootstrap 按配置开关，与会话清理等一起挂在 `startBackgroundTasks`）

## 12. 最值得讲的工程点

### 12.1 不是“一个大模型”，而是双轨多 Agent 系统

- 职责拆分清晰
- 流程边界清楚
- 更容易控风险

### 12.2 中断恢复做成了真实工程能力

- 可暂停
- 可审批
- 可恢复
- 可断点继续

### 12.3 状态分层设计比较完整

- Session Memory 管对话记忆
- compact 中间件管实时上下文压缩
- Checkpoint 管执行恢复
- Graph State 管结构化工作流状态

### 12.4 执行安全边界不是口头承诺

- 静态风险校验
- 权限系统（allow / deny / ask）
- 运行时审批
- 重复失败熔断
- 契约门（执行前证据校验）
- 最终人工兜底

## 13. 面试时的标准介绍版本

可以这样介绍：

> OnCall 是一个面向 Kubernetes 值班运维的多 Agent 系统。它不是单纯问答，而是把故障处理拆成了两条链路：一条是 `dialogue_agent` 对话链，负责意图识别、检索、slash 命令和轻量工具调用；另一条是 `incident_workflow_agent`，基于 `agentteams` 编排，按 `Loop(incident_analysis -> diagnosis_gate -> plan -> plan_gate -> plan_approval -> execute_plan -> verify_plan -> replan_decider) -> final_report` 跑完整处置闭环。
> 在工程上我重点做了三件事：第一，用 Redis Checkpoint + ADK Resume 实现高风险步骤中断审批和断点恢复；第二，用 Session Memory、compact 中间件、Graph State 分层管理状态，既控制 token，又支持长流程恢复；第三，用 `plan_gate + plan_approval + execute_step + verify_plan + replan_decider` 把执行安全做成可校验、可审批、可恢复、可熔断的机制。

## 15. 总结

这个项目最像后端工程而不是“Prompt Demo”的地方，在于它把故障处理过程真正做成了一个受控系统：有分层、有状态、有恢复、有审批、有熔断，也有最终的知识沉淀。对外看是 AI 运维，对内本质上是一套可执行、可审计、可恢复的工程化工作流。
